# UI Reference and Asset Resolution

## Resolution order

Before formal UI production:

1. Decompose UI requirements and useful component patterns from the user's requirement materials or competitor references.
2. Inspect approved same-project pages to calibrate hierarchy, layout, color, material, typography, control shape, and state expression.
3. Reuse approved project components before modifying them or proposing new ones.
4. Use approved project concept art for characters, creatures, environments, and other identity-bearing art.
5. Check configuration tables when UI content depends on item, reward, activity, or icon mappings.

Competitor references explain structure; they are not project-owned assets and do not establish current-project rules.

## Asset classification

Classify each major element as one of:

- project component;
- modified project component;
- temporary placeholder;
- proposed new component;
- external reference.

Add a short source note beside the output. Never present generated or external material as an existing project asset.

## Search record

Keep a compact record of:

- searched library path;
- keywords and feature area;
- selected references;
- rejected near matches and why;
- missing assets;
- new or modified components created.

## New outputs

Archive every new reusable component separately from the final composite UI. Use versioned filenames and preserve approved bases. When a requested change affects only an overlay, line, label, or state treatment, edit the approved base rather than regenerating the entire page.

## Multi-state UI

- Baseline state: label and define all shared components.
- Difference state: label and define only components whose display, state, or interaction result changed.
- Preserve component letters across states.
- Verify copy, numbers, completion marks, enabled/disabled treatment, countdowns, reward quantity, and action outcome against the adjacent specification.
- When the requirement calls for many rewards, allocate enough visible area and use a readable grid; do not replace a requested 10+ item display with a few token examples.

## Marker rules

Letter markers over a UI image and letter blocks in the explanation area are different objects and may have different styles. Markers over the UI must be independent, editable, unobstructed, and on the top layer. Check actual visibility in the native document application; object counts and coordinates alone are insufficient.
